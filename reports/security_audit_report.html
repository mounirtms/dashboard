Injection Vector Analysis (June 12 Afternoon):
The Monolog payload was uploaded through Magento's Customer Address file upload endpoint (customer/address/upload). Evidence:
  • The file landed in pub/media/customer_address/s/e/ — the exact path created by Magento's FileProcessor::moveTemporaryFile() using Uploader::getDispersionPath()
  • The filename sess_3p0yzmiw02nqj28855nq2kncveepr6g6 mimics a PHP session file but sessions are stored in Redis (not files), confirming deliberate placement
  • The payload contained a Monolog BufferHandler gadget chain designed to execute shell_exec() via PHP deserialization, downloading a second-stage backdoor from GitHub

Root Cause Analysis — Upload Vulnerability (June 13 Evening):
The SessionReaper attacks persisted because of a missing database configuration for file upload protection:
  • Vulnerability: Magento's general/file/protected_extensions config path was not set in the database. The framework's default XML config only blocks php, php3, php4, php5, php7 — but NOT php8, session files (sess_*), or other dangerous types
  • Bypass mechanism: When $allowedExtensions is empty (no file_extensions validation rule on the attribute), Magento's Uploader::checkAllowedExtension() returns true for ALL extensions — effectively allowing any file type to be uploaded
  • The .php8 extension was specifically chosen by the attacker to evade the default blocklist which only covered php through php7
  • Session files (sess_*) have no file extension at all, bypassing extension-based validation entirely
Fix Applied:
  • Set general/file/protected_extensions in core_config_data to block 34 dangerous file types: php, php3, php4, php5, php7, php8, phps, phtml, pht, phar, phpt, pgif, htaccess, ini, user.ini, jsp, pl, py, asp, aspx, sh, bash, csh, ksh, cgi, exe, dll, com, bat, cmd, hta, shtml, svg, svgz
  • Config cache flushed to apply immediately
  • Defense-in-depth: .htaccess in upload directories continues to block PHP execution for all extensions including .php8
  • Defense-in-depth: .user.ini with engine = off disables PHP entirely in upload directories
Exploit Impact: Access logs showed the attacker attempted to reach 81e627ea7d2b.php (target webshell) since May 5 — every attempt returned 404. The secondary payload was never downloaded. Attack failed due to defense-in-depth layers.
